# ADR 0001: UI 프레임워크 — tcell 직접 사용 + 자체 컴포지터

- 상태: **채택** (2026-11-04)
- 관련: SPEC 5장(기술 스택), 6장(아키텍처), 9.0(지원 대상), [compat-matrix](../compat-matrix.md)

## 배경

tuidesk는 터미널 안에서 겹치는 창을 마우스로 옮기고, 한글 파일명을 다루며, 폐쇄망 서버에 바이너리 하나로 들어가야 합니다. Phase 0에서 확인한 요구사항은 다음과 같습니다.

1. **겹치는 창 합성**: z-order, 창 단위 클리핑, 일부만 가려진 창.
2. **한글(2칸 글자) 처리**: 다른 창의 테두리가 한글의 오른쪽 반만 덮는 경우에도 화면이 깨지면 안 됩니다. 셀 단위로 제어해야 합니다.
3. **입력 정규화를 직접 다뤄야 함** (compat-matrix 발견 1~5, 7)
   - 클릭, 더블클릭, 드래그는 앱이 판별해야 합니다. release가 누락되는 터미널이 있고, 우클릭은 드래그로 판별하지 않습니다.
   - 한글 입력 상태의 Ctrl+자모(`Ctrl+ㅊ`)를 QWERTY 키로 바꿔야 합니다.
   - 리눅스 콘솔에서는 Shift+F10이 `F20`으로 들어오고, Shift/Ctrl+방향키의 수정키가 사라집니다.
4. **지원 대상 두 곳**: macOS Terminal.app(ssh 접속, 256색, 마우스), 리눅스 콘솔(8색, 키보드 전용, 한글 글꼴 없음).
5. **배포**: `CGO_ENABLED=0` 정적 바이너리이고, 폐쇄망 반입을 위해 `go mod vendor`를 씁니다. 의존성은 적을수록 좋습니다.
6. **이벤트 기반 렌더링**: 유휴 시 CPU 사용률이 거의 0이어야 합니다.
7. **에디터**: micro의 버퍼, 하이라이트 코드를 이식할 계획입니다(SPEC 5장).

## 검토한 선택지

### A. tcell v2 직접 사용 + 자체 컴포지터 (기본안)
- tcell은 화면 I/O만 맡습니다. 창 관리, 합성, 입력 판별은 tcell에 의존하지 않는 순수 Go 코드(`internal/term`, `internal/wm`)로 작성합니다.
- **Phase 0에서 실제로 만들고 검증했습니다.**
  - `internal/wm`
    - `Canvas`: 셀 버퍼입니다. 2칸 글자의 반쪽이 덮이면 나머지 반쪽을 비웁니다. 클리핑 경계에 걸린 2칸 글자는 공백으로 대체합니다.
    - `Manager`: z-order, 히트테스트, 포커스 순환, 제목줄 드래그 이동, 화면 밖으로 사라지지 않게 위치 보정.
  - `cmd/wmdemo`: 겹치는 창 3개를 마우스 드래그나 키보드(Tab, 방향키)로 옮깁니다.
  - 테스트
    - tcell 시뮬레이션 화면에서, 아래에 깔린 창의 제목줄을 끌어 옮기면 맨 앞으로 올라오고 새 위치에 그려지는지 확인합니다.
    - 한글이 겹치는 경우(덮인 반쪽, 클리핑 경계)의 셀 일관성 검사.
  - 리눅스 콘솔(QEMU VT)에서 렌더링과 키보드 이동을 확인했습니다. 결과 화면은 `img/wmdemo-linux-console*.png`입니다.
  - 규모: 로직, 데모, 테스트를 합쳐 약 1,700줄입니다. 외부 모듈은 tcell, go-runewidth와 그 하위 의존성(모두 Apache-2.0/MIT/BSD)뿐입니다.

### B. Bubble Tea v2 (+ Lip Gloss v2)
- 창 관리자 사례로 TUIOS가 있습니다. Elm 아키텍처(Model/Update/View)를 쓰고, 위젯 생태계(bubbles)가 풍부합니다.
- 장점: 목록, 입력창 같은 위젯을 재사용할 수 있습니다. v2는 마우스 누름, 뗌, 이동을 서로 다른 메시지로 구분하는 것으로 알고 있습니다. 이 구분은 발견 1(release 누락 대비)에 유리합니다.
- 우려
  - View가 문자열을 반환하는 구조입니다. 겹치는 창과 한글 반쪽 가림 같은 **셀 단위 합성**을 하려면 결국 레이어 합성 기능에 의존하거나 직접 만들어야 합니다.
  - 입력 정규화(자모 정규화, F20 처리, 우클릭 정책)는 어느 쪽을 쓰든 직접 해야 합니다.
  - 의존성 트리가 더 큽니다(charmbracelet/x 계열 여러 개). 폐쇄망 vendoring과 라이선스 고지 범위가 늘어납니다.
  - micro는 tcell 기반이라, 에디터 코드를 이식할 때 중간 변환 계층이 필요합니다.
- **이번에 프로토타입을 만들지 않았습니다.** SPEC은 두 방식을 프로토타입으로 비교하라고 했습니다. 하지만 A안이 완료 기준을 이미 만족했고, 아래 결정 이유 1~3이 B안을 쓰더라도 사라지지 않는 비용이어서 생략했습니다. 위 B안의 장단점 중 v2 API에 대한 내용은 검증하지 않은 추정입니다.

### C. tview (tcell 위의 위젯 라이브러리)
- 위젯은 많지만, 레이아웃이 타일형(Flex/Grid/Pages) 중심입니다. 자유롭게 겹치고 움직이는 창에 맞지 않아 제외했습니다.

## 결정

**A안, tcell v2를 직접 쓰고 컴포지터를 직접 만듭니다.** (SPEC의 기본안을 유지합니다.)

이유
1. **셀 단위 제어가 필수입니다.** 한글 반쪽 가림, 창 클리핑, 이후 Phase 1의 더티 영역 렌더링은 셀 버퍼를 직접 다뤄야 깔끔합니다. Phase 0에서 이미 구현하고 테스트했습니다.
2. **입력 정규화는 어차피 직접 해야 합니다.** 이번 호환성 테스트의 발견(자모, F20, 우클릭, release 누락)은 프레임워크가 해결해 주지 않습니다. tcell은 이벤트를 가장 날것에 가깝게 줍니다.
3. **의존성이 가장 작습니다.** 폐쇄망 vendoring과 라이선스 고지 부담이 적습니다.
4. **micro 이식 경로가 짧습니다.** micro가 tcell 위에서 동작하기 때문입니다.
5. **이벤트 기반 루프가 단순합니다.** `PollEvent` → 상태 갱신 → 그리기 구조라서, 타이머 외에는 깨어날 일이 없습니다.

## 결과와 후속 작업

- **위젯을 직접 만들어야 합니다(Phase 1 비용).** 메뉴, 컨텍스트 메뉴, 다이얼로그, 리스트, 스크롤바, 토스트가 대상입니다. tcell에 의존하지 않는 상태 로직과, Canvas에 그리는 코드로 나눠 테스트합니다.
- **tcell의 `EventMouse`는 누름과 이동을 구분하지 않습니다.** release가 누락되면 다음 클릭이 드래그로 오인될 수 있습니다. 지원 대상(Terminal.app)에서는 문제가 없었으므로 Phase 1에서 최소한의 방어만 검토합니다. 예를 들어, 버튼을 누른 채 위치가 크게 튀면 새 누름으로 간주합니다.
- **tcell은 시작할 때 확장 키 프로토콜(CSI-u)을 켭니다.** 그래서 한글 입력 상태에서는 Ctrl+자모가 들어오고, 이는 `term.ShortcutRune`으로 처리합니다. 키맵 계층을 만들 때는 반드시 이 함수를 거치게 합니다.
- **화면 출력**: Canvas의 2칸 글자 오른쪽 반 칸에는 아무것도 쓰지 않습니다. tcell 렌더러가 그 칸을 건너뛰기 때문입니다(`cmd/wmdemo` 참고).
- **다시 검토할 조건**
  - Phase 1 위젯 작업이 예상보다 크게 늘어날 때. 예를 들어 위젯 하나에 며칠씩 걸리는 경우입니다.
  - tcell 유지보수가 멈추거나, 지원 대상 터미널에서 tcell로 풀 수 없는 문제가 나올 때.
